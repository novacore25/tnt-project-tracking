# Laporan Audit Mendalam — TNT Project Tracking System
### Commit `fba7c36` · Branch `main` · 30 September 2026

> Audit statis terhadap kode. **Tidak ada akses ke database produksi**, jadi klaim tentang
> constraint/index diverifikasi dari file migration di `web-app/supabase/migrations/` —
> yang merupakan sumber kebenaran DDL — bukan dari `\d` langsung.
>
> **Semua temuan sudah diverifikasi ulang sebelum ditulis di dokumen ini.** Angka metrik
> (jumlah baris, `useState`, `alert`) dihitung langsung dari file.

## Ringkasan Eksekutif

Sistem ini **fungsional dan dipakai setiap hari** — 1.068 commit, 40 route, 6 jalur ingestion,
dashboard yang benar-benar dipakai tim. Fondasi teknologinya benar: Next.js App Router,
server actions, PostgreSQL, domain model yang masuk akal.

Masalahnya **bukan di pilihan teknologi, tapi di lapisan konsistensi**. Empat pola berulang
menyebabkan hampir semua temuan di dokumen ini:

| Pola | Akibat |
|---|---|
| **Otorisasi hanya di client** | `canEditCampaign()` hanya mengubah tampilan tombol. ~190 dari 239 server action tidak punya guard yang bermakna. User `staff` bisa memanggil apa saja. |
| **Tidak ada transaksi** | 5 tahap import berjalan tanpa transaksi. Kegagalan tengah = data setengah jadi. `importLiveOrganicAction` bisa kehilangan data produk secara permanen. |
| **Store dikosongkan paksa** | `useDatabaseStore.ts:145-164` meng-`[]` kan `creators`, `campaign_creators`, `videos`. Tiga modal sync jadi tidak bisa mencocokkan username — **fitur mati tanpa error**. |
| **Tidak ada invalidasi client** | 101 `revalidatePath()` tidak berefek untuk halaman client. User tidak pernah tahu datanya basi. |

### Temuan paling serius (bukan 20-item daftar, tapi 3 yang harus pertama diketahui)

**1. Otorisasi secara teknis tidak ada.**
`updateProfileAction` (`databaseActions.ts:1248`) tidak punya cek auth sama sekali dan menerima
`{ role, status }` dari client. **User `staff` bisa mengeset role dirinya jadi `admin`** dalam
satu panggilan. Twin-nya yang di-gate (`manajemen-akun/actions.ts:59`) jadi tidak berarti.
Seluruh rantai approval pembayaran (23 fungsi) memanggil `auth()` lalu **tidak pernah mengecek
hasilnya** — termasuk `financeMarkPaid` yang menandai pembayaran lunas.

**2. GMV bisa masuk campaign yang salah, dan tidak ada yang tahu.**
`tiktokAutoSync.ts:503-510` mencocokkan nama campaign dengan `includes()` **dua arah** tanpa
batas panjang. Campaign internal bernama `TNT` akan cocok dengan campaign TikTok mana pun yang
namanya mengandung "TNT". Semua order & konten produk campaign itu langsung ditulis ke
campaign yang salah. **Tidak ada konfirmasi user, tidak ada log, tidak bisa di-revert kecuali
sync ulang dari nol.**

**3. Data hilang diam-diam di setiap sync.**
`tiktokAutoSync.ts:717-722` membuang semua video yang `campaign_id IS NULL` dengan satu
`console.log`.-video tersebut tidak masuk `tiktok_sync_logs.details`, tidak ditampilkan ke user.
Laporan sync bisa membaca "500 konten" padahal 3.000 tidak masuk. Além itu
`organic_videos` dengan `product_id` NULL **selalu diduplikasi** setiap sync, karena
`ON CONFLICT (content_uid, product_id)` tidak pernah terpicu saat `product_id` NULL.

### 1.2 Pola arsitektur yang dipakai (dan harus dipertahankan)

**Client-heavy, bukan server-rendered.** 65 dari 109 komponen `.tsx` adalah `"use client"`.
Halaman besar ambil datanya sendiri lewat server action di `useEffect`, bukan dari store.
Mengubah ini ke Server Component = rewrite besar. **Jangan.**

**Raw SQL, bukan Drizzle query builder.** Hampir 100% query adalah `db.execute(sql\`...\`)`.
Drizzle = pool manager + typed parameter binding + type-only schema. Konsekuensi: tidak ada
compile-time check nama kolom, dan kesalahan nama kolom tertangkap `.catch(() => [])` di banyak
tempat → **kehilangan data senyap**.

**Server action = API.** Tidak ada REST untuk CRUD. Konsekuensi keamanan: **server action
adalah endpoint publik yang tidak memperhatikan UI sama sekali.**

## Bagian 2 — Database

### 2.1 `src/db/schema.ts` tidak cocok dengan database nyata

| Tabel | `schema.ts` bilang | Database nyata bilang |
|---|---|---|
| `payment_batches` | `batch_code`, `batch_type`, `total_amount` | `batch_label`, `submitted_by`, `*_reviewed_by`, `paid_by`, `bukti_transfer_url`, `sender_account_id` |
| `payment_items` | `amount` | `nominal`, `ratecard_awal`, `biaya_transfer`, `actual_transfer` |
| `sales` | `gross_sale`, `refund`, `buyer_payment` | `gmv BIGINT`, `is_refund BOOLEAN` |
| `ads_performance` | `cost`, `gmv`, `impressions`, `clicks` | `cost_usd`, `gross_revenue_usd`, `kurs NUMERIC` |
| `daily_performance` | 9 kolom counter | **VIEW** dengan 2 kolom |

**8 tabel tidak ada di `schema.ts`** (23% entitas runtime): `live_sessions`, `live_session_products`,
`live_schedules`, `payout_requests`, `payout_creator`, `creator_payments`, `ads_allocations`,
`pembayaran`. Kolom `ads_performance.creator_id` dan `sales.campaign_creator_id` juga hilang —
padahal dipakai di 6 file.

`schema.ts` juga **nol deklarasi `index()`**. Semua index dibuat manual lewat SQL.

> 🔴 **Jangan pernah `drizzle-kit push`.** Itu akan menghapus unique constraint
> `sales.order_id` dan merusak dedupe order. Perubahan skema = file SQL baru di
> `web-app/supabase/migrations/`.

### 2.2 Constraint yang hilang padahal kode mengandalkannya

| Yang dibutuhkan | Bukti kode | Dampak |
|---|---|---|
| `campaign_creators (campaign_id, creator_id)` UNIQUE | check-then-insert di 4 tempat | Baris duplikatcreator per campaign |
| `videos.content_uid` UNIQUE | `syncUnmapped.ts:144` | Duplikat video |
| `videos (campaign_creator_id, urutan)` UNIQUE | `MAX(urutan)+1` di 3 tempat | Nomor video bentrok/bolong |
| `organic_videos (content_uid, product_id)` saat `product_id` NULL | `ON CONFLICT` `importActions.ts:183` | **Duplikat setiap sync** |
| `ads_performance` unique | `INSERT` polos `importActions.ts:465` | Upload 2× = dobel |
| `profiles.email` lowercase-unique | semua query `LOWER(email)=?` | `A@x.com` dan `a@x.com` = 2 profile |

### 2.3 Index yang hilang → full table scan

`sales` punya 6 index. Yang dipakai kode tapi tidak ada:
`sales.campaign_creator_id`, `sales.order_status`, `organic_videos (campaign_id, content_uid)`,
`organic_videos (lower(creator_username))` — yang terakhir penting karena query-nya
`LOWER(col)=LOWER(?)` (`creatorActions.ts:174`), yang **tidak bisa** memakai B-tree index biasa.

### 2.4 Relasi yang terputus (string-based, tanpa FK)

`organic_videos.creator_username`, `sales.campaign_creator_id`, `ads_performance.creator_id`,
`videos.content_uid`, `user_campaigns.user_id`, `ads_topups.sender_account_id`.
Bridge `content_uid` ini yang menghubungkan `videos` ↔ `organic_videos` ↔ `sales` — dan
**tidak punya unique index**, jadi dedupe 100% bergantung kode aplikasi.

### 2.5 Tiga sumber kebenaran yang bisa berbeda

**Status bayar**: `payment_items.final_status` (baru) vs `campaign_creators.status_bayar`
(legacy, ditulis dari **dua** tempat tanpa transaksi) vs `creator_payments.status_bayar` (legacy).

**Role**: `profiles.role` vs `whitelisted_emails.role` vs `users.role` (tabel `users` nyaris mati).

**GMV**: 5 sumber tumpang tindih. `vw_campaign_summary` di-`CREATE OR REPLACE` **6× dalam 6 bulan**
dengan logika berbeda — phase_2 menjumlahkan 3 sumber, phase_5 memakai `GREATEST()`.
**Angka "achievement GMV" berubah definisi setiap kali view di-update.**

### 2.6 Penyimpanan uang

Rupiah bulat (`bigint`) aman. Yang bermasalah: `NUMERIC` **tanpa skala** untuk `skus.komisi` dan
`ads_performance.kurs` (default 16000) — tidak ada `ROUND()` di mana pun; dan
`daily_performance` pakai `NUMERIC(15,2)` yang **overflow** untuk GMV > ~10 triliun,
dengan error yang tertangkap `.catch(() => [])` → kehilangan data senyap.

### 2.7 RLS adalah keamanan semu

`20260628000000_enable_rls.sql` meng-enable RLS di semua tabel dengan policy
`USING (true) WITH CHECK (true) TO authenticated`. Tapi aplikasi **tidak pernah pakai Supabase
client** — konek langsung via `postgres-js` (`db/index.ts:14`). RLS karena itu: tidak pernah
melihat context `authenticated`, dan di-bypass karena koneksi pakai user pemilik tabel.
Ditambah 4 tabel yang dibuat **setelah** migration itu tidak pernah dapat RLS sama sekali.

**Semua scoping 100% di level aplikasi.** Kalau aplikasinya tidak cek, database juga tidak cek.

## Bagian 3 — Autentikasi & Otorisasi

### 3.1 Gerbang (`proxy.ts`)

Hanya mengecek **keberadaan** cookie `authjs.session-token` (`proxy.ts:14-18`) — nilainya tidak
diverifikasi. Public path: `/login`, `/api/auth`, `/auth`, `/portal` (seluruh prefix).

### 3.2 Identitas (`auth.ts`)

`signIn` callback (`auth.ts:33-85`): query `whitelisted_emails` → **diabaikan**; kalau role kosong,
email mengandung `"admin"` atau `"executive"` → `role = 'executive'`, selain itu `'staff'`;
profile baru dibuat `status='approved'`; **`return true` di baris 80, selalu**.

→ **Siapa pun dengan akun Google masuk.** Email `attacker-admin@gmail.com` dapat executive penuh.
Duplikat di `storeActions.ts:40-47`.

### 3.3 Otorisasi hanya di client

`canEditCampaign()` (`AuthProvider.tsx:71-80`) adalah satu-satunya implementasi ACL.
Halaman keuangan fetch data **tanpa gate** (`keuangan/page.tsx:49-54`);
`hasAccess` hanya membungkus 2 blok JSX.

**Dari 22 modul `'use server'`, hanya 2 punya guard otentikasi efektif:**
`manajemen-akun/actions.ts` dan `portal/actions/portalActions.ts`.
Seluruh **`paymentActions.ts` (46 fungsi)**, `campaignPageActions.ts` (45), `databaseActions.ts` (45),
`creatorActions.ts` (13), `tiktokShopActions.ts` (14), `addressActions.ts` (9), `importActions.ts` (10),
`skuActions.ts` (6) — tidak punya guard yang bermakna.

### 3.4 Reachability — apa yang bisa dilakukan siapa

| Tindakan | Anonymous | `staff`/`anggota` |
|---|---|---|
| `updateProfileAction` (`databaseActions.ts:1248`) |-Blokir proxy | **Set role sendiri jadi `admin`** |
| `updateUserCampaignsAction` (`databaseActions.ts:1272`) | Blokir proxy | **Self-grant `all_campaigns`** |
| `financeMarkPaid` / `bulkMarkPaidFinance` (`paymentActions.ts:1009`/`:1322`) | Blokir proxy | **Tandai pembayaran lunas** |
| `updateCreatorPaymentAction` (`databaseActions.ts:524`) | Blokir proxy | Tandai kreator `lunas` |
| `getInitialStoreData` (`storeActions.ts:104`) | Blokir proxy | Semua campaign + profile + role |
| `deleteCampaignAction` (`storeActions.ts:250`) | Blokir proxy | Hapus campaign (+cascade) |
| `deleteSkuAction` (`storeActions.ts:304`) | Blokir proxy | `campaignId` **hanya untuk `revalidatePath`**, tidak masuk `WHERE` |
| `updateClientNotes` (`portalActions.ts:775`) | **Akses langsung** (proxy public) | Tulis ke campaign mana pun, tanpa cek PIN |
| `POST /api/expand-tiktok` | **SSRF** (cookie name-only) | SSRF |
| `POST /api/sync-unmapped` `syncAll:true` | Blokir proxy | Tulis global |
| `POST /api/sync/tiktok-manual` | Blokir proxy | Sync campaign mana pun |
| `GET /api/cron/tiktok-sync` | **Terbuka jika `CRON_SECRET` unset** | Sama |

### 3.5 SQL injection: diperiksa, tidak ditemukan

`sqlInList` (`db/index.ts:28-31`) aman — setiap elemen jadi bound parameter, array kosong → `IN (NULL)`.
Nol `sql.raw`/`sql.unsafe`/`client.unsafe` di seluruh `src`.

Dua pola rapuh (Low, bukan exploitable sekarang):
- `storeActions.ts:155,197` — satu-satunya SQL literal yang dirakit manual (`text[]`).
  Saat ini aman karena di-bind sebagai parameter, tapi satu refactor dari jadi injection.
- `paymentActions.ts:720` — `ILIKE %${nama}%`. Parametris, jadi bukan SQLi; risikonya semantik
  (pola `%` dari user bisa memilih `picId` yang salah).

### 3.6 SSRF di `/api/expand-tiktok`

`api/expand-tiktok/route.ts:7-15` validasi hanya `shortUrl.includes('vt.tiktok.com')`.
`String.includes` bisa di-bypass: `http://169.254.169.254/latest/meta-data/#vt.tiktok.com`
lolos. Dengan `redirect: 'follow'`, server melakukan request outbound ke jaringan internal
dan mengembalikan URL hasilnya → **cloud metadata read primitive**.

### 3.7 Portal brand

PIN 4-digit, **tanpa rate limit**, plaintext di cookie dengan `secure: false`.
Default PIN campaign baru = `'1234'` (`storeActions.ts:177,228`).
`batchUpdateResiByClient` (`portalActions.ts:746-773`) melakukan IDOR lintas campaign —
bandingkan versi single-record (`:707-717`) yang **benar** dan bisa jadi pola.

## Bagian 4 — Pipeline Data

### 4.1 Idempotensi

| Tabel | Conflict target | Masalah |
|---|---|---|
| `sales` | `ON CONFLICT (order_id)` | ✅ aman. **Tapi `order_id` punya 2 skema berbeda**: Excel import = komposit (`OrganicImport.tsx:425`), auto-sync = ID TikTok mentah (`tiktokAutoSync.ts:348`). Keduanya jalan untuk periode yang sama → **order dobel, GMV dobel**. |
| `organic_videos` | `ON CONFLICT (content_uid, product_id)` | ⚠️ `product_id` NULL → conflict tidak pernah terpicu → **duplikat setiap sync** |
| `videos`, `campaign_creators` | check-then-insert | ❌ race-prone |
| `ads_performance` | `INSERT` polos | ❌ upload 2× = dobel |
| `live_session_products` | DELETE-then-INSERT tanpa transaksi | ❌ crash di tengah = **data hilang permanen** |

### 4.2 Tidak ada transaksi

`db.transaction` dipakai di **satu tempat** seluruh aplikasi: `listingActions.ts:127`.
`importActions.ts`, `syncUnmapped.ts`, `tiktokAutoSync.ts` = **nol**.

`executeSalesImportChunkAction` (`importActions.ts:33-352`) menjalankan 5 tahap:
sales → organic_videos → creators → campaign_creators → videos. Tahap 4 gagal setelah tahap 1-3
sudah commit → response `{success: false}` padahal **data sudah masuk**. User melihat "Data Gagal".

### 4.3 Rate limit / retry / timeout

`callTikTokShopApi` (`tiktokShopApi.ts:268-321`) tidak punya **satu pun**: timeout, retry,
backoff, handling 429, rate limit.

Beban satu sync: `96 campaign × 10 produk × 50 kreator × 2 = ~96.000 HTTP call`, sequential
per campaign/produk. `Promise.all` di `:612` tanpa batas bisa menembakkan ratusan request
konkuren sekaligus.

`maxDuration = 60` di `api/cron/tiktok-sync/route.ts:5` **tidak realistis** — sync penuh butuh
puluhan menit. `/api/sync/tiktok-manual` tidak punya `maxDuration` sama sekali.

### 4.4 DDL per-request

| Lokasi | DDL | Frekuensi |
|---|---|---|
| `tiktokShopApi.ts:254-278` | `CREATE TABLE` + 4× `ALTER TABLE` | **tiap polling UI (3-15 detik × user)** |
| `tiktokAutoSync.ts:688-739` `ensureVideoColumns()` | `DO $$ ALTER TABLE × 20 $$` | **tiap render halaman `/campaigns/[id]/video`** |

`ALTER TABLE` ambil lock `ACCESS EXCLUSIVE` yang kontend dengan INSERT dari sync yang sama.
`campaignPageActions.ts:720-722` memakai `EXCEPTION WHEN OTHERS THEN NULL` → **error DDL
ditelan diam-diam**.

### 4.5 O(n²) yang jadi bottleneck

`tiktokAutoSync.ts:393` — `salesRowsToInsert.some(...)` per SKU per order. 10.000 order × 1,5 SKU
= **150 juta iterasi**. Ini bottleneck utama auto-sync. `:185`, `:423`, `:656` serupa.

### 4.6 Memori tidak terikat

`tiktokAutoSync.ts:226-227` menahan seluruh `salesRowsToInsert` + `videoRowsToInsert` di memori
sampai akhir sync. `raw_data` menyimpan **objek order TikTok lengkap** (`:419`) → 20-40MB untuk
10.000 order. Tidak ada chunking (padahal `importActions.ts:363` sudah punya polanya).
Tidak ada checkpoint — gagal di menit ke-45 membuang 45 menit kerja.

### 4.7 Token TikTok

| Aset | Lokasi | Masalah |
|---|---|---|
| `app_key`/`app_secret` | hardcoded fallback `tiktokShopApi.ts:4-5` | Di git history |
| `access_token`/`refresh_token` | `TEXT` **plaintext** di DB | Tanpa enkripsi/vault |
| `access_token`/`refresh_token` | `localStorage['tts_*']` | XSS → token dicuri, valid ~365 hari |
| `app_secret` | **query string GET** `tiktokShopApi.ts:41-47` | Bocor ke access log, proxy log, `Referer` |
| Scoping | `WHERE status='active' ORDER BY id DESC LIMIT 1` | **Tidak ada** — hanya 1 seller/instalasi |

**Bug refresh** (`tiktokShopApi.ts:251-262`): kalau refresh gagal (token expired/revoked), fungsi
**tetap return `{ isValid: true, accessToken: <token mati> }`**. Tidak ada notifikasi
"re-authorize required".

### 4.8 "Unmapped" — konsep yang paling sering membingungkan

Baris dengan `campaign_id IS NULL` karena `product_id`-nya belum terdaftar di `skus`.
**Datanya lengkap** — hanya tidak punya alamat campaign.

⚠️ **Risiko finansial utama:** `syncUnmappedForProduct` (`syncUnmapped.ts:31-45`) UPDATE sales
dengan `WHERE campaign_id IS NULL AND product_id = X` **tanpa filter tanggal** dan tanpa
konfirmasi. Satu klik "Simpan" di SKU Detective bisa **mengubah GMV historis campaign secara
retroaktif**. Dan kalau `product_id` sama terdaftar di 2 campaign, **SKU pertama menang**
secara diam-diam.

Tidak ada halaman "Unmapped Report" — user harus scroll `console.log`.

### 4.9 Fuzzy matching

| Lokasi | Dampak |
|---|---|
| `stringSimilarity.ts:55` (threshold 50%) | ⚠️ longgar (`anna`↔`anna1` = 80%), tapi **hanya saran** — user wajib klik. **Desain yang benar, jangan diubah jadi otomatis.** |
| `tiktokAutoSync.ts:503-510` (match nama campaign) | 🔴 **Otomatis, tanpa review, berdampak GMV.** Lihat §Ringkasan poin 2. |

## Bagian 5 — Frontend & UX

### 5.1 Store adalah "shell" yang sebagian besar kosong

`useDatabaseStore.ts:138-173` (`fetchData`) secara eksplisit mengosongkan 8 koleksi utama:
`creators: []`, `creator_snapshots: []`, `campaign_creators: []`, `videos: []`,

Hanya 7 key yang terisi: `brands`, `campaigns`, `niches`, `skus`, `vw_campaign_summary`,

**Dampaknya langsung dan diam-diam:** `CampaignSyncModal.tsx:15-16`, `CreatorSyncModal.tsx:18`,
`AddressSyncModal.tsx:17-18` membaca `creators` untuk daftar username → **selalu array kosong** →
`findClosestMatch` tidak pernah menemukan kandidat, badge "Valid" tidak pernah muncul.

### 5.2 Data bisa rollback tanpa jejak

`VideoClient.tsx:363` — `fetchApprovedCreators` selalu `setHasMore(false)`, jadi tombol
"load more" mati permanen setelah fetch pertama.

(RSC props) ke local state **setiap kali props berubah**. RSC memberi array baru tiap navigasi,
jadi setiap `router.refresh()` **menimpa hasil fetch manual** yang mungkin lebih baru.

### 5.3 Ganti akun tanpa reload

`DataLoader.tsx:11` `hasFetched` ref tidak di-reset. `AuthProvider.tsx:47-69` fetch profile
sekali di mount. Setelah `signOut` → `signIn` sebagai user lain, store masih berisi data user
**sebelumnya** sampai full reload.
